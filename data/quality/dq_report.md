## Why each finding matters

### DQ-02 - (case_id, timestamp) uniquely identifies an event (WARN)
**Observed:** 14,118 rows share a (number, sys_updated_at) pair (10.0%)

**Implication:** Timestamps are minute-precision, so several updates within the same minute collapse onto one value. The fact table therefore needs a surrogate event key and an explicit within-case sequence number, not a natural key.

### DQ-05 - Columns at least 90% unknown are identified (WARN)
**Observed:** caused_by 99.98%; vendor 99.83%; cmdb_ci 99.69%; rfc 99.3%; problem_id 98.38%

**Implication:** These carry almost no signal. They are excluded from the dimensional model rather than shipped as near-empty attributes that invite false conclusions.

### DQ-06 - Every incident_state is a recognised process activity (WARN)
**Observed:** 5 events in unrecognised states: {'-100': 5}

**Implication:** Sentinel values like '-100' are source-system artefacts, not real process steps. Left in, they appear as a phantom activity in the process map.

### DQ-07 - Cases ending in Resolved/Closed carry a resolved_at timestamp (WARN)
**Observed:** 1,556 of 21,668 terminal cases have resolved_at unknown

**Implication:** Cycle time cannot be computed for these; they must be excluded from the cycle-time denominator rather than counted as zero duration.

### DQ-08 - closed_at is distributed, not concentrated on batch timestamps (FAIL)
**Observed:** 2,707 distinct values over 141,712 events; top 5 = {'24/3/2016 18:59': 3324, '24/3/2016 18:50': 2846, '24/3/2016 18:40': 2808, '24/3/2016 19:00': 2780, '24/3/2016 19:01': 2044}

**Implication:** A handful of timestamps account for a large share of all closures: an automated bulk-close job, not real agent activity. closed_at is therefore NOT a valid basis for cycle time. resolved_at is used instead.

### DQ-09 - made_sla is constant across all events of a case (FAIL)
**Observed:** 9,114 of 24,918 cases (36.6%) change made_sla mid-case

**Implication:** made_sla is a live evaluation that flips the moment the clock is breached, not a static outcome. Counting it at event grain would overstate attainment. The case-grain fact must take the LAST observed value per case.

### DQ-12 - Case-level attributes are stable across a case's events (WARN)
**Observed:** cases with more than one distinct value: {'priority': 383, 'category': 1216, 'contact_type': 5, 'caller_id': 3}

**Implication:** Attributes that change mid-case cannot be modelled as static case dimensions; the case-grain fact takes the last observed value, consistent with DQ-09.
